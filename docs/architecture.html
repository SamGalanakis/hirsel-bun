Current Architecture

One project, one shepherd, many visible threads.

Hirsel is now backend-first. The desktop app is a thin shell that stores backend connection details and loads the backend-served Datastar UI. The durable product model is project + shepherd + canvas + threads, with coding work executed as queued scope turns against project workspaces.

Important: threads are durable product objects, but their coding turns are not in-process. Each queued shepherd or thread turn runs through the hidden hirsel __shepherd-scope-runtime for that scope.

Project

Top-level unit of work.

  • One starting point
  • One central checkout
  • One shepherd conversation
  • One canvas artifact
  • Many visible threads

Shepherd

The only agent the user talks to directly.

  • Answers simple questions directly
  • Creates, renames, updates, archives, deletes, and messages threads
  • Owns integration decisions in the central checkout

Canvas

A separately-authored HTML artifact stored on the backend.

  • Rendered on the project page
  • Updated by shepherd through a narrow tool surface
  • Intended for synthesis, comparisons, and current project state

Execution Model

Central Checkout

The first time a project needs workspace materialization, Hirsel creates a central checkout at ~/.hirsel/workspaces/project-<id>/work/central. This becomes the integration base that shepherd reasons over and that thread checkouts branch from.

Thread Checkouts

Each visible thread gets its own checkout under the same project workspace, usually at .../work/thread-<slug>-<id>. The checkout path and checkout name are stored on the thread record.

Scope Runtime

When a queued turn runs, the backend starts the hidden scope runtime for that shepherd or thread scope against the appropriate workspace.

Scope State

Each scope keeps durable session state and a workspace path so shepherd and threads can resume work against the correct checkout.

HTTP Surface

The live UI is page/action/SSE based rather than a client-owned SPA store.

Current Constraints

  • Coding turns are queued scope executions rather than continuously running workers.
  • Shepherd owns the central checkout; isolated work should live in visible thread workspaces.
  • Thread titles, statuses, and summaries are part of the user-facing product surface and should stay understandable.
  • Backend route composition and project UI composition still own too many concerns.
