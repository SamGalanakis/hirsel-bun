Current Architecture

One project, one shepherd, many visible threads.

Hirsel is now backend-first. The desktop app is a thin shell that stores backend connection details and loads the backend-served Datastar UI. The durable product model is project + shepherd + canvas + threads, with coding work executed in Docker containers that enter the repo through nix develop.

Important: threads are durable product objects, but their coding turns are not in-process. Each queued shepherd or thread turn launches the hidden hirsel __shepherd-scope-runtime inside a Docker container.

Project

Top-level unit of work.

  • One starting point
  • One central checkout
  • One shepherd conversation
  • One canvas artifact
  • Many visible threads

Shepherd

The only agent the user talks to directly.

  • Answers simple questions directly
  • Creates, renames, pauses, archives, and messages threads
  • Owns integration decisions in the central checkout

Canvas

A separately-authored HTML artifact stored on the backend.

  • Rendered on the project page
  • Updated by shepherd through a narrow tool surface
  • Intended for synthesis, comparisons, and current project state

Execution Model

Central Checkout

The first time a project needs workspace materialization, Hirsel creates a central checkout at ~/.hirsel/workspaces/project-<id>/work/central. This becomes the integration base that shepherd reasons over and that thread checkouts branch from.

Thread Checkouts

Each visible thread gets its own checkout under the same project workspace, usually at .../work/thread-<slug>-<id>. The checkout path and checkout name are stored on the thread record.

Container Runtime

When a queued turn runs, the backend launches a Docker container, mounts /work, /hirsel, session home, and the hidden hirsel binary, then enters the repo through nix develop.

Flake Bootstrapping

Project scope may bootstrap a temporary shell if the project has no flake.nix yet. Thread scope is stricter: normal coding threads require the project flake to exist first.

HTTP Surface

The live UI is page/action/SSE based rather than a client-owned SPA store.

Current Constraints

  • Docker is a hard requirement for coding turns.
  • Normal thread execution requires a project flake.nix.
  • The deploy image serves the backend UI, but full coding execution still expects the backend process to have Docker available on its host.
  • The biggest remaining code hotspots are still web_routes.rs and webui.rs, which own too many concerns each.
