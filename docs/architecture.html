Interaction Architecture

Hirsel should feel like a conversation that keeps condensing itself into a visible project focus.

This page reframes Hirsel from a worker dashboard into a project-level architecture: Shepherd is the primary control surface, the user stays focused on the project rather than individual routes, and the right-hand surface becomes a dynamic HTML focus view while routes and task machinery continue underneath.

2 — Screen Blueprint

The main product is a project surface, not a route switcher attached to a board.

Shepherd stays present on the left as the user’s continuous conversational partner. The right side becomes a dynamic focus view: the HTML artifact Shepherd updates to show what the user should currently pay attention to. Routes can fork and run in parallel underneath, but they are visualized jointly at the project level rather than as separate workspaces the user has to enter.

3 — Interaction Loop

Shepherd should update the project focus view only when the user’s attention should actually move.

The goal is not “generate a new explainer every turn.” The goal is to maintain a durable representation with stable structure and selective updates. That creates continuity, trust, and a tactile sense that the project is being actively worked rather than theatrically reimagined from scratch.

Step 01

Free-text input

The user talks to Shepherd naturally. No mandatory fields, templates, or route forms are required up front.

→
Step 02

Project-state update

Shepherd interprets the message as changes to intent, constraints, questions, decisions, or work progression at the project level.

→
Step 03

Route orchestration decision

Shepherd decides whether to continue within the current route, fork additional routes, compare active routes, or keep gathering evidence.

→
Step 04

Focus-view edit

A constrained tool updates the existing self-contained HTML focus view. It can become a comparison, diagram, code excerpt, preview surface, or brief depending on what the user should see now.

→
Step 05

Joint route visualization

The UI renders the latest project focus by default and only surfaces minimal route metadata—count, short labels, and status—unless deeper machinery is explicitly requested.

The key product constraint is calmness. The focus view should feel maintained, not regenerated. Stable objects, stable placement, and selective edits matter more than maximum visual cleverness.
4 — Artifact Model

The product has to distinguish between project focus, route execution, machinery, and retained understanding.

Hirsel already has routes, board state, docs, delivery, and Shepherd chat. The new architecture clarifies their roles instead of inventing a separate authoring model.

Project

User-facing unit

The user works at the project level: what we are trying to do, what matters now, and what may need a decision.

Focus view

Dynamic HTML artifact

The user-facing condensation of what Shepherd thinks matters now. Stable, inspectable, and incrementally editable.

Docs / memory

Retained understanding

The broader project state promoted into durable references: conventions, architecture notes, usage guidance, and lessons.

Routes

Parallel execution branches

Routes remain real and may fork freely, but Shepherd manages their lifecycle and the UI summarizes them jointly rather than as separate user workspaces.

Machinery

Execution substrate

Tasks, workers, evals, repair loops, and logs remain necessary, but they serve the project rather than define the whole product.

Delivery

Publication boundary

Delivery becomes the act of crystallizing project outcomes into code, PRs, docs, and promoted memory, not merely pushing a branch.

5 — Current vs Target

The target architecture is new in emphasis, not completely new in ingredients.

The current product already contains most of the substrate: Shepherd chat, projects, routes, SpecBoard, docs, messaging, and delivery. The change is that these should be re-read through a product architecture where Shepherd and the project focus view sit on top of the machinery instead of beside it.

6 — Runtime Appendix

The runtime still matters. It just no longer deserves to be the first thing this page says.

The current implementation already has substantial technical infrastructure beneath the interaction model. This appendix keeps the runtime story visible without letting it dominate the product architecture.

Current layout composition

Project surface + machinery reveal

  • Layout.tsx now renders a persistent ShepherdConsole plus a project-level focus surface
  • ProjectSurface.tsx owns the right-hand HTML artifact and the machinery reveal
  • SpecBoard, runs, workers, memory, and route switching now live under machinery tabs instead of driving the whole shell
State and route substrate

Routes already provide the right persistence boundary

  • Global DB stores projects, routes, board nodes, and Shepherd history
  • Route folders already hold scoped docs and task content files
  • Delivery already operates at the route/version level
Execution runtime

Shepherd and workers remain runtime-backed

  • Shepherd messages execute real turns and stream events to the UI
  • Workers remain isolated execution contexts operating on assigned board work
  • The project focus view now sits above this runtime instead of replacing it
This is the hybrid position: product architecture first, runtime architecture second. The page should help a reader understand what Hirsel is becoming while staying honest about the infrastructure it already has.

File layout
  • ~/.hirsel/hirsel.db stores global config, credentials, projects, routes, board state, and Shepherd history

  • ~/.hirsel/runs/{run_name}/hirsel.db stores per-run lifecycle state, workers, events, evals, and history
  • Run workspaces live under ~/.hirsel/runs/{run_name}/work/ with staging and worker-specific worktrees

Configuration, orchestration traits, and runtime patterns
Core traits
  • Orchestrator has local, daemon, and remote implementations
  • LifecycleManager has local and remote variants
  • Runner covers host execution plus optional containerized execution on that host
  • Workspace and archive behavior are abstracted behind provider / strategy traits
Configuration model
  • Config is loaded DB-first from the global store with file-based defaults and persistence helpers
  • Key fields include agent config, eval timeout, HITL default, one backend connection target, named runners, and storage
  • The client stores the backend URL/API key it should connect to; there is no multi-profile orchestrator model in the current code
Cross-cutting patterns
  • Error handling is centralized under core/error.rs with categorized error kinds
  • Process management utilities live in core/process.rs
  • state_access.rs abstracts worker access over SQLite or HTTP
  • Board export/import bridges the route tree to filesystem-editable artifacts for AI tooling
HTTP API and IPC reference surfaces
Run and worker HTTP families
  • /api/runs for run CRUD, workspace initialization, spawn, pause, resume, and delivery
  • /api/runs/{name}/workers/* for worker listing, restart, spawn, resume, and event access
  • /api/runs/{name}/evals, /history, and message thread endpoints support run-specific inspection and coordination
Board, config, and IPC families
  • /api/board/{project_id}/* covers board export/import and task-file operations
  • /api/config and /api/credentials/* cover config and credential CRUD
  • Tauri IPC is the primary frontend surface for runs, drafts, workers, delta board operations, Shepherd chat, docs, project messages, routes, delivery, and IDE integration
  • Shared route builders split between build_shared_routes(), config-only routes, board-only routes, and daemon-specific inline endpoints
