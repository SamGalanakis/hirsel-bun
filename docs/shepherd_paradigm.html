The Shepherd Paradigm

Replace mechanical orchestration with an intelligent agent that drives the flock.

The Problem

Hirsel currently splits intelligence across disconnected stages. The user talks to a legacy chat agent, plans on a static board, hits dispatch, and a mechanical daemon takes over — assigning tasks to workers through heuristic scaling with zero domain knowledge.

Every handoff loses context. The chat layer knows what the user wants but can’t control execution. The daemon assigns tasks but doesn’t understand them. Plan workers decompose features but can’t see how other features went. It’s a game of telephone.

The Shift

The Shepherd paradigm merges the chat layer, Dispatch, and the Lifecycle Manager into a single intelligent agent — the Shepherd. You talk to the Shepherd. The Shepherd drives the flock.

Before (Legacy Chat + Daemon)

  • Chat agent has no control over execution
  • Daemon assigns tasks with heuristics, no understanding
  • Board is both planning surface and execution driver
  • Rigid dispatch pipeline — always plan then execute
  • Repair loops are mechanical, not intelligent
  • User intent is lost after the board is drawn

After (Shepherd)

  • The agent you talk to IS the one running the show
  • Assignments made with full domain context
  • Board becomes a live view of orchestration
  • Decomposition is dynamic — Shepherd decides when and how
  • Failures are handled intelligently with re-planning
  • User intent flows from conversation to execution

Who Does What

Role Responsibility Replaces

Workers Execute assigned tasks in isolated processes. Fresh context per task. Report results back through DB state. Unchanged — same runner infrastructure

How It Flows

1

Conversation

User describes what they want in natural language. The Shepherd understands intent, asks clarifying questions, proposes an approach. This is how work begins — not by drawing boxes on a board.

2

Decomposition

The Shepherd breaks down the work into tasks, decides ordering and dependencies. It populates the board as a side effect — so the user can see the plan taking shape. No rigid plan-then-execute pipeline; the Shepherd can decompose progressively as it learns.

3

Assignment & Execution

The Shepherd assigns tasks to workers with full context about what matters. It knows which tasks are most critical, which can run in parallel, and what context each worker needs. Workers execute in isolated processes — same runner infrastructure, same process model.

4

Monitoring & Adjustment

As workers report results, the Shepherd evaluates progress. If a task fails, it doesn’t mechanically spawn a repair — it understands what went wrong and re-plans. It can reassign work, change priorities, add new tasks, or skip unnecessary ones.

5

Delivery

The Shepherd knows when the work is truly done — not just “all tasks complete” but whether the user’s original intent is satisfied. It can validate, summarize what was done, and hand off for delivery.

Principles

Context flows, not fragments

User intent travels from conversation to decomposition to assignment without translation layers or static artifacts in between.

Board is a view, not the driver

The board visualizes what the Shepherd is doing. Users observe and intervene. Orchestration is driven by intelligence, not by parsing node state.

Workers stay isolated

Workers are still separate processes with fresh context per task. The Shepherd pattern changes who assigns work and how — not how work gets done.

Dynamic over rigid

No mandatory plan-then-execute pipeline. The Shepherd decomposes progressively, re-plans on failure, and skips unnecessary steps. The approach adapts to the work.

Durability through state

The Shepherd writes its decisions to the board (SQLite). If it restarts, the board is recovery state. Workers don’t depend on the Shepherd being alive.

User stays in control

The Shepherd is not autonomous. It proposes, the user approves. The user can pause, redirect, reprioritize, or take over at any point through natural conversation.

Why Not Full Recursive Subagents?

The REPL/subagent model (where agents spawn agents that spawn agents) is tempting but has real limits at this scale:

Context window ceiling

An orchestrator managing 5–10 concurrent workers over minutes-to-hours of execution exhausts its context. Claude Code’s Task tool works because subagent tasks are short-lived. Hirsel workers can run much longer.

Fragile root

If the orchestrator dies in a full recursive model, the entire tree collapses. The Shepherd model mitigates this: decisions are checkpointed to the board, workers are independent processes, the Shepherd can resume from persisted state.

Observability

A recursive agent tree is a black box. The Shepherd writes to the board as it works — users see a live, structured view of what’s happening. Transparency by design, not by debugging.

The Shepherd is one level of intelligence above the workers — not a recursive tree. It’s the farmer talking to a sheepdog, not a bureaucracy of middle managers spawning sub-managers. Workers don’t spawn sub-workers. The Shepherd decides everything, delegates execution, watches results.

What Changes, What Stays

Changes

  • Legacy chat layer becomes the Shepherd — gains orchestration powers
  • Dispatch goes away as a rigid pipeline
  • Plan workers likely absorbed into the Shepherd
  • Eval becomes a tool the Shepherd invokes, not an automatic trigger
  • Daemon simplifies to pure process management
  • Board is written to by the Shepherd, not read from as the source of truth

Stays

  • Worker process model (runners, isolation, fresh context)
  • SQLite state persistence
  • Board visualization (SpecBoard, ELK layout, all of it)
  • Runner infrastructure (Local, SSH, Fly)
  • MCP tools for workers
  • Delivery pipeline (git operations)
