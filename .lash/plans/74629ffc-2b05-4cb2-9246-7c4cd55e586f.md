# Plan

## Goal
- Restructure Hirsel’s Cargo layout so there is one real top-level workspace with shared dependency pinning, while preserving both current product surfaces:
  - root/server CLI flow used by `just`, `cargo build`, and `target/debug/hirsel`
  - desktop/Tauri app and related server/worker binaries currently under `src-tauri`

## Recommendation
- Yes, a larger Cargo layout restructure is optimal.
- The repo currently has two separate Cargo workspace roots (`Cargo.toml` and `src-tauri/Cargo.toml`) and both define a package named `hirsel`.
- That blocks a true shared workspace dependency pin and guarantees drift in dependencies, lockfiles, and build commands.
- Best target state:
  - root `Cargo.toml` becomes a workspace root only
  - shared Rust application logic lives in a dedicated crate, e.g. `crates/hirsel-core`
  - the current root binary becomes a dedicated app crate, e.g. `crates/hirsel-cli`
  - `src-tauri` remains the desktop app crate, renamed at the package level to avoid duplicate package names, e.g. `hirsel-desktop-app`
  - all shared dependencies, including `lash`, move to `[workspace.dependencies]`
  - one workspace `Cargo.lock` at repo root

## Why this is the optimal path
- Fixes the actual structural problem instead of papering over duplicate pins.
- Eliminates duplicate backend trees over time by giving both CLI/server and Tauri a common library crate.
- Makes `cargo check --workspace`, `cargo clippy --workspace`, and shared lockfile management straightforward.
- Keeps the Tauri-specific crate isolated from non-desktop builds.
- Preserves room for feature-gated binaries without forcing Tauri into every build.

## Why not the smaller alternatives
- Keeping two standalone manifests and manually syncing pins:
  - low effort now, but guaranteed drift later
  - still two lockfiles and two build surfaces
- Making root and `src-tauri` one workspace without refactoring package names:
  - Cargo rejects duplicate package names in one workspace
- Making `src-tauri` depend directly on the root package as a library without first separating concerns:
  - awkward because the root manifest is currently both workspace root and application package
  - still leaves unclear ownership of shared code and build artifacts

## Target end-state
- `Cargo.toml` at repo root:
  - `[workspace]`
  - `members = ["crates/hirsel-core", "crates/hirsel-cli", "src-tauri"]`
  - `default-members = ["crates/hirsel-cli"]`
  - `[workspace.dependencies]` for shared crates including `lash`
  - shared lints/profiles if desired
- `crates/hirsel-core/Cargo.toml`
  - package name `hirsel-core`
  - contains shared backend logic now duplicated between `src/backend` and `src-tauri/src/backend`
- `crates/hirsel-cli/Cargo.toml`
  - package name `hirsel-cli`
  - owns the `hirsel` binary users run from `just`
  - depends on `hirsel-core`
- `src-tauri/Cargo.toml`
  - package name changed to something unique like `hirsel-desktop-app`
  - depends on `hirsel-core`
  - keeps Tauri-only code in `src-tauri/src/desktop` and Tauri-specific setup in `src-tauri/src/lib.rs`
- One workspace lockfile at `Cargo.lock`
- Delete `src-tauri/Cargo.lock`

## Proposed rollout steps

### Phase 1: Establish one workspace shell
- Convert root `Cargo.toml` from package+workspace hybrid into workspace root for the repo.
- Add member crates:
  - `crates/hirsel-core`
  - `crates/hirsel-cli`
  - `src-tauri`
- Rename the `src-tauri` package so it no longer collides with the CLI package.
- Move shared dependency pins into `[workspace.dependencies]`.
- Keep behavior the same; do not deduplicate source yet.

### Phase 2: Create shared core crate
- Move the active shared backend implementation into `crates/hirsel-core/src`.
- Likely source of truth should be today’s root `src/backend` tree because the repo tooling (`Justfile`) already targets the root app.
- Export the APIs both app frontends need:
  - server startup
  - worker/server entrypoints
  - shared config, DB, runtime, skills, etc.
- Keep app-specific glue out of core.

### Phase 3: Rewire app crates
- `crates/hirsel-cli`:
  - move current root `src/main.rs`, `src/lib.rs`, `build.rs`, and any CLI-only version plumbing here
  - depend on `hirsel-core`
- `src-tauri`:
  - replace duplicated backend modules with imports from `hirsel-core`
  - retain only Tauri-specific code, desktop commands, and any desktop-only adapters

### Phase 4: Remove duplication
- Delete duplicated Rust modules from one side after the shared core is wired in.
- Update docs, scripts, and CI commands to use workspace-aware invocations.
- Remove `src-tauri/Cargo.lock`.

## Concrete file moves likely needed
- Root package files to new CLI crate:
  - `src/main.rs` -> `crates/hirsel-cli/src/main.rs`
  - `src/lib.rs` -> likely split between `crates/hirsel-core/src/lib.rs` and `crates/hirsel-cli/src/lib.rs` or removed if unnecessary
  - `src/version.rs` -> shared core or CLI depending on usage
  - `build.rs` -> `crates/hirsel-cli/build.rs` if still needed there
- Shared backend modules:
  - `src/backend/**` -> `crates/hirsel-core/src/backend/**`
- Tauri package cleanup:
  - keep `src-tauri/src/desktop/**`
  - keep `src-tauri/src/bin/hirsel-desktop.rs`
  - re-evaluate whether `hirsel-server` and `hirsel-worker` should remain in `src-tauri/src/bin` or move to CLI/app crates

## Naming recommendation
- Workspace root: no `[package]`, workspace only
- Shared library crate: `hirsel-core`
- CLI/server app crate: `hirsel-cli`
- Tauri app crate: `hirsel-desktop-app`
- Binary names can remain user-facing:
  - `hirsel`
  - `hirsel-server`
  - `hirsel-worker`
  - `hirsel-desktop`

## Build command changes
- Current:
  - `cargo build`
  - `cargo run --manifest-path src-tauri/Cargo.toml ...`
- Proposed:
  - `cargo build -p hirsel-cli`
  - `cargo run -p hirsel-cli -- serve ...`
  - `cargo run -p hirsel-desktop-app --bin hirsel-desktop`
  - `cargo run -p hirsel-desktop-app --no-default-features --features server --bin hirsel-server`
- `Justfile` should be updated to target package names explicitly instead of assuming the root package binary path.

## Risks
- Large file movement across already-changing parts of the repo.
- Tauri build assumptions may rely on package-local paths and build scripts.
- Version/build metadata may currently be duplicated in both roots.
- Docs and deployment examples explicitly reference `--manifest-path src-tauri/Cargo.toml`; those need coordinated updates.
- If the root and `src-tauri` backends have diverged semantically, choosing the wrong source of truth could reintroduce regressions.

## Risk mitigation
- Do Phase 1 first with minimal behavior change.
- Keep package renames mechanical and verify each build target before deduping code.
- In Phase 2, choose one backend tree as the canonical source and move only that one into `hirsel-core`.
- Diff corresponding files in `src/backend` and `src-tauri/src/backend` before deleting duplicates.
- Update docs/Justfile/CI in the same change that removes old manifest-path assumptions.

## Verification
- Phase 1:
  - `cargo metadata --format-version 1`
  - `cargo check -p hirsel-cli`
  - `cargo check -p hirsel-desktop-app --all-targets`
- Phase 2/3:
  - `cargo check --workspace`
  - targeted runs for server and desktop bins
  - confirm `lash` resolves once from workspace dependencies
- Final:
  - one `Cargo.lock` at root
  - no `src-tauri/Cargo.lock`
  - no duplicate `lash` pins outside `[workspace.dependencies]`
  - no duplicate package names in workspace metadata

## Suggested execution order if we implement this
1. Rename packages and create real workspace members.
2. Move root app into `crates/hirsel-cli`.
3. Introduce `crates/hirsel-core` from the chosen backend source of truth.
4. Rewire `src-tauri` to `hirsel-core`.
5. Remove duplicate backend files and old lockfile.
